# Formalizing a paper on top of LMLExplore

A paper project formalizes one paper: its main results, stated in Lean, proved, and verified by
comparator. It builds on [LMLExplore](https://github.com/LeanMachineLearning/LMLExplore), and Tau
Ceti workers port its library-shaped part to LMLExplore while the formalization goes on. The
repository is made from
[lml-paper-template](https://github.com/LeanMachineLearning/lml-paper-template).

Below, `<Lib>` is the Lean library (`Maiti2026Power`: first author, year, first word of the
title), `<Paper>` the folder of the paper's own results (`MXJ2026`), and `<KEY>` the citation key
of the paper (`MXJ26`).

How this skill was invoked decides what to do:

- **No argument, or a paper** (an arXiv identifier, a URL, a PDF): the interactive workflow below,
  with the user. In a new repository, start with `bootstrap.md`.
- **`round`**: one unattended round, see [Unattended rounds](#unattended-rounds). No user is
  present.
- **`bump`**: move to a newer LMLExplore, see [The bump](#the-bump).

Companion files in this directory: `bootstrap.md` (from the template to the first push) and
`tools.md` (where each tool lives, and the gotchas collected so far). The `paper-roadmap` skill
of this plugin owns `PAPER_ROADMAP.md`.

## Layout of a project

- `source/`: the paper. `notes/blueprint-outline.md`: the paper decomposed into labelled lemmas
  before any Lean is written. `notes/*.md`: design decisions. `notes/paper-errata.md`: the
  errors found in the paper, see [Errata](#errata).
- `blueprint/src/chapters/*.tex`: the leanblueprint. Part I follows the paper; Part II holds the
  library-shaped prerequisites.
- `<Lib>/ForLMLExplore/`: library-shaped material, with no paper-specific object. It uses
  LMLExplore's layout and namespaces (`LMLExplore.<Area>.…`, at the path LMLExplore would use)
  and LMLExplore's rules, see [Library-shaped code](#library-shaped-code), so that a port is
  close to a copy. `<Lib>/<Paper>/`: the paper itself, one file per result.
- `PAPER_ROADMAP.md`: one row per prerequisite, tagged `exists`, `target`, `refactor`, `staged`
  or `paper`, with its status. The `paper-roadmap` skill writes it, and the Tau Ceti workers read
  it to know what to port.
- `formalization.yaml`: the headline statements, and the `status` section (phases, sorry counts,
  what changed and when). For each headline result, also its literature-links relation and its
  errata entry, if any. `comparator/`: one self-contained challenge per headline theorem,
  generated, never hand-edited.
- `literature/bibliography.json`: the works cited, for the literature links.
- Every file is `module` + `public import` + `@[expose] public section`; the root `<Lib>.lean`
  is generated by `lake exe mk_all --lib <Lib>` (CI checks it with `--check`).

## Dependencies

The project requires LMLExplore at one commit, recorded in `lake-manifest.json`, and gets
Mathlib, Tau Ceti and LML at the versions LMLExplore pins. Never require those at other
revisions. The LMLExplore pin moves only in [the bump](#the-bump): once at the end, or at an
LMLExplore sync when the user asks for a newer Mathlib. Build with `scripts/build.sh`, whose
arguments go to `lake build`: it fetches Mathlib's and Tau Ceti's prebuilt files first.

## Workflow

1. **Outline first** (`bootstrap.md`, step 3). The outline fixes every label and proof route.
   For each prerequisite, search LMLExplore, Tau Ceti, LML and Mathlib first, up to renaming,
   generalization and definitional unfolding, and reuse what exists. Decide the modelling there
   (for colt-2026-83: LML's `IsAlgEnvSeq` framework on an arbitrary probability space,
   identification algorithms as sampling + stopping + output rules, stopping times as Mathlib
   `hittingAfter`), then write the blueprint chapters from it.
2. **Phase 1, statements.** Define the objects in library generality (a generic
   finite-dimensional inner product space rather than `EuclideanSpace`, measures with implicit
   `{mX : MeasurableSpace X}` binders when a measure fixes the σ-algebra, no abbreviations that
   only save typing). State each headline result with `sorry` and list it in
   `formalization.yaml` (an entry of `alignment.statements`). Then go through the statements with
   the user, against the paper. Each gets its literature-links relation (the entry's `relation`
   key), and each error of the paper that this check finds gets an errata entry (named by the
   entry's `erratum` key). Only then generate the comparator challenges
   (`bootstrap.md`, step 6). The challenges freeze the statements: phase 2 must prove exactly
   them.
3. **End of phase 1.** Tell the user that the rest can run unattended: `scripts/formalize.sh`, in
   a terminal or tmux, outside the agent session. Phase 2 can also go on in a session, by the
   same rules.
4. **Phase 2, proofs, blueprint-driven.** Before attacking a large target, expand the blueprint
   into a sequence of small labelled lemmas with `\uses`. Then formalize one coherent area at a
   time (a whole prerequisite chapter), not scattered one-step lemmas. Prove the general
   statement and derive the paper's as a one-line specialization. Library-shaped results go to
   `ForLMLExplore/`. State laws as `HasLaw`/`HasCondDistrib`, not `Measure.map` equations; keep
   a bare `Measure.map` equality only when both sides are unknown laws. Give conditional
   divergences in both composition-product (`_compProd`) and integral (bare name) forms.
5. **Keep everything in sync as you go.** Each Lean declaration gets its `\lean{Full.Name}` tag
   and `\leanok` the moment it compiles (proof `\leanok` too). Drop hypotheses the Lean proof
   does not use and say so in the docstring. Cite the paper's numbered results in docstrings, see
   [Literature links](#literature-links). `theorem` only for headline results and big classical
   theorems, `lemma` for everything else; grep for `^theorem` before finishing. An item of
   `PAPER_ROADMAP.md` whose files are proved, with no `sorry`, gets the status `proved`.
6. **Record.** Update `formalization.yaml` (`status`), `PAPER_ROADMAP.md`, `notes/`, the errata
   and the README.

## Library-shaped code

`ForLMLExplore/` follows LMLExplore's `AGENTS.md`, which LMLExplore's reviewers enforce on every
port:

- the copyright header, then `module`; Mathlib's linter set with warnings as errors (style,
  header, files of at most 1500 lines);
- no `set_option`, no `maxHeartbeats` override, no `native_decide`, no axioms beyond `propext`,
  `Classical.choice` and `Quot.sound`;
- no meta code: no elaborators, `run_cmd`, `#eval`, nonlocal macros or custom term syntax;
- every definition comes with the basic API that makes it usable, at the generality of the
  literature, with docstrings.

The paper's CI runs LMLExplore's lint and axiom checks on this folder.

## Literature links

The project records which declarations formalize which results of the paper, in the
[Literature Links](https://github.com/mathlib-initiative/literature-links) format and with the
conventions of LMLExplore's literature page (`scripts/literature/README.md` in LMLExplore), so
that the links survive a port.

- **Cite numbered results in docstrings**, or in an entry of a `## Main ...` list of the module
  docstring, which links the result to the declarations that the entry names in backquotes
  before its colon: `[MXJ26, Theorem 1]`, `[MXJ26, Lemmas 3.2, 3.3]`, `[MXJ26, Lemmas 4.1–4.3]`,
  `[MXJ26, Theorem 6 (a)]`, `[MXJ26, proof of Theorem 5]`, `[MXJ26, (17)]`. A citation of a whole
  work, `[MXJ26]`, gives no link. Library-shaped code cites its own sources the same way
  (`[LS, Theorem 11.2]`). A module that cites a work also lists it in its `## References`
  section.
- **`literature/bibliography.json`** describes each cited work by its key: `uri` (its arXiv page,
  DOI or publisher page), `citation` (a CSL-JSON item), `identifiers` (`{"arxiv": "…"}`), and
  `version`, the revision whose numbering the citations use (`v2` of an arXiv preprint), when it
  is not the published one. LMLExplore's `scripts/literature/lookup.py propose` drafts entries.
- **The relation of each headline result**, set during the phase-1 statement check, is the
  `relation` key of its entry in `alignment.statements` of `formalization.yaml`, read "paper
  *relation* Lean":
  - `exactMatch`: the same claim, up to notation and junk values;
  - `closeMatch`: nearly the same, with a difference a reader should know, such as a convention
    or a corrected constant;
  - `broadMatch`: the Lean statement is more general;
  - `narrowMatch`: the paper's statement is more general, for instance when a correction adds a
    hypothesis;
  - `hasPart`: the Lean statement is one claim of the result.
- **CI** writes the annotations from the dataset that the referee site extracts, with
  LMLExplore's `annotations.py` at a pinned commit, adds the relations, checks the result with
  `literature-links validate`, and publishes it beside the blueprint.

## Errata

Every error found in the paper goes to `notes/paper-errata.md`: during the phase-1 statement
check, during proofs, and in unattended rounds. A deviation from the paper that is not a
generalization always has an entry; never fix the paper silently. One section per error:

```markdown
## E3. Lemma 4.2: the constant is 1/4, not 1/2

- **Where:** arXiv:2501.01234v2, Lemma 4.2, page 12, equation (17).
- **Error:** the last step bounds … by …, which only gives ….
- **Correction:** … (with the argument, or a pointer to the Lean proof).
- **Lean:** `Maiti2026Power.MXJ2026.lemma_4_2` states the corrected form.
- **Kind:** typo, wrong constant, missing hypothesis, gap in the proof, or false statement.
- **Found:** phase-1 statement check, or round of 2026-11-08 (commit abc1234).
```

Number the entries `E1`, `E2`, … and never renumber them. A headline result stated in corrected
form names its entry in the `erratum` key of its `alignment.statements` entry in
`formalization.yaml`. The file is meant to be sent to the authors as it
is: keep it factual and self-contained.

## Unattended rounds

After phase 1, `scripts/formalize.sh` runs `claude -p "/lml:formalize-paper round"` in a loop. No
user is present.

- **Never ask the user.** Decide, and record the decision in `notes/`. Do only what the
  repository's permission list allows; a denied command is a reason to find another way, or to
  record why the job is blocked, not to stop the round.
- **The statements are frozen.** Never change the comparator challenges, `comparator/targets.txt`
  or the statements of the headline results. If a headline result turns out false or unprovable
  as stated, write its errata entry, set the `status` of its `alignment.statements` entry to
  `blocked`, and print `Blocked: <result>` at the end of the round. Later rounds skip blocked
  results; the user decides.
- **Do the first job that applies, commit it, then stop:**
  1. **Tag.** `PAPER_ROADMAP.md` has no items yet: follow the tagging procedure of the
     `paper-roadmap` skill.
  2. **Refresh.** LMLRoadmaps `main`, or the paper's pull requests to LMLExplore, changed since
     the header of `PAPER_ROADMAP.md`: follow the refresh procedure of the `paper-roadmap`
     skill.
  3. **Refactor pull request.** An item tagged `refactor` is `proved` and has no pull request:
     open it, see [below](#refactor-pull-requests).
  4. **Advance.** A headline result or a blueprint item is not proved (blocked results aside):
     take one area of the blueprint, such as a chapter, or a main result with the prerequisites
     it still needs. Prefer an area whose dependencies are proved and that unblocks the most.
     Push it as far as the session gets, following the workflow above: proofs, blueprint tags,
     citations, errata, statuses in `PAPER_ROADMAP.md`.
  5. **Nothing applies:** print `Nothing to do` and stop.
- **Before committing:** `scripts/check-build.sh` and `lake exe runLinter <Lib>` pass,
  or the round reverts what broke them; `lake exe mk_all --lib <Lib>` after adding or removing a
  module; `lake build Comparator` when a definition in the closure of a headline statement
  changed. Never run the full comparator verification: `formalize.sh` runs it once, at the end.
- **One commit per round**, whose message names the job and the area. Push to `origin`, when the
  repository has one (a paper kept local has none). Never
  rewrite history or force-push.
- Outside the paper repository, a round only opens refactor pull requests to LMLExplore. It opens
  no issue or pull request anywhere else.

### Refactor pull requests

1. Fork LMLExplore if needed (`gh repo fork LeanMachineLearning/LMLExplore --clone=false`), and
   keep a clone of the fork in `.tauceti/LMLExplore`, with `upstream` pointing to
   `LeanMachineLearning/LMLExplore`.
2. Branch from `upstream/main`, and make the change of the item following LMLExplore's
   `AGENTS.md`: only `LMLExplore/`, one topic, every use updated, no aliases or deprecations.
   `scripts/build.sh` in the clone must succeed with no warnings.
3. Open the pull request against `main`, titled `refactor: …`. The body says what changes, lists
   each removed or renamed public declaration with what replaces it, and ends with the standalone
   lines `Roadmap: none`, `Paper: <owner>/<repo>` and `Item: <Id>`.
4. Set the item's status to `PR #<number>`, and commit.

The PR worker that `formalize.sh` runs answers the review of these pull requests.

## The bump

Run once at the end by `formalize.sh`, or at an LMLExplore sync when the user asks for it.

1. `lake update LMLExplore`, copy `.lake/packages/LMLExplore/lean-toolchain` to `lean-toolchain`,
   and run `scripts/build.sh`. Check that the Mathlib, Tau Ceti and LML commits in
   `lake-manifest.json` are those of `.lake/packages/LMLExplore/lake-manifest.json`.
2. Collect what changed in LMLExplore between the two pins: the removed and renamed declarations
   that the descriptions of the merged pull requests list, and the paper's merged ports
   (status `merged` in `PAPER_ROADMAP.md`).
3. For each merged port, and each item LMLExplore now has: delete the local copy in
   `ForLMLExplore/`, move every use to the LMLExplore declaration, and keep what is additional
   (more general results, extra lemmas), re-proved on top of LMLExplore. Retag the item `exists`.
4. Apply the renames to the rest of the project, and rebuild with `scripts/check-build.sh`.
5. Declarations that moved change the names in the closure of the headline statements:
   regenerate the challenges (`python3 scripts/make-challenges.py`) and check, with a diff, that
   each statement is unchanged up to those names.
6. Commit, with the old and the new pin in the message.

## Looking things up

- API at the pinned versions: grep `.lake/packages/LMLExplore`, `.lake/packages/TauCeti`,
  `.lake/packages/LeanMachineLearning` and `.lake/packages/mathlib`; use the web only to compare
  with a newer `main`.
- Try statements in a scratch file (`lake env lean File.lean`) with `#check`, `#synth`,
  `#print`, `example … := rfl` to test definitional bridges before relying on them;
  `exact?`/`fun_prop` for closing goals.
- Import needed? `LEAN_PATH=$(lake env printenv LEAN_PATH) lean File.lean --setup
  .lake/build/ir/<Module>.setup.json`, no lake lock taken.

## Checking your work

Run after every batch of Lean edits, in this order:

```
scripts/check-build.sh                 # whole library; every warning but sorry fails it
lake exe runLinter <Lib>               # Mathlib linters; fix everything it reports
grep -rn "sorry" <Lib>                 # must be empty at the end of phase 2
grep -rn "^theorem" <Lib>              # only headline/classical results
lake exe mk_all --lib <Lib>            # after adding or removing a module
```

Blueprint, after any `.tex` change (PDF before web, since web reuses the bibliography):

```
python3 scripts/check-blueprint.py     # env balance, labels, \uses, \input, bib keys
leanblueprint pdf && leanblueprint web # from the repository root
lake exe checkdecls blueprint/lean_decls   # every \lean{} tag names a real declaration
```

`blueprint/lean_decls` is generated by the web build, never edited. To see all LaTeX errors at
once: `cd blueprint/src && xelatex -interaction=nonstopmode -output-directory=../print print.tex`
then `grep -n -A3 "^! " ../print/print.log`.

Comparator, whenever a headline statement or a definition in its closure changes:

```
python3 scripts/make-challenges.py     # challenge-gen: imports LMLExplore, copies the project's defs
lake build Comparator                  # no --wfail: "uses sorry" warnings are expected here
scripts/comparator-verify.sh --insecure   # 10–15 min; in a session, only when asked; run detached
```

Detached long runs: `setsid nohup … > log 2>&1 &` (background Bash has a ten-minute cap), and
never `pkill -f` a pattern that matches the launching shell. In a session, never commit unless
the user asks, and ask before the full comparator run; unattended rounds commit as described
above.
